# Включение настоящих подписанных обновлений — действия владельца

Задание #10, ветка `feat/issue-6-auto-updates`, база PR #9. Владелец проверил ручной
запуск выбранного EXE на Windows 10. Это не подтверждает онлайн-обновление.
Код проверки/установки можно проверить без сети, но **настоящие обновления ещё не
включены**: `launcher/trust.py` пуст, подписанного публичного Release нет.
Эта задача не создаёт ни ключ владельца, ни draft, ни опубликованный Release.

## 1. Подготовить локальный инструмент

На **вашем компьютере**, после просмотра кода, откройте PowerShell в checkout:

```powershell
py -3.12 -m venv .venv-release-tools
.venv-release-tools\Scripts\python.exe -m pip install -r requirements-launcher.txt
.venv-release-tools\Scripts\python.exe tools/prepare_signed_release.py --help
```

После установки зависимостей keygen/inspect/sign/verify могут работать полностью
офлайн. Утилита не содержит GitHub API, не загружает файлы и не публикует Release.
`keygen`/`sign` требуют интерактивного терминала; пароль нельзя передать параметром,
переменной CI или pipeline. В GitHub Actions эти подкоманды заблокированы.
Тесты CI используют только одноразовые тестовые ключи и временные файлы вне checkout.

## 2. Создать ключ вне всех Git checkout

Выберите **новый** приватный каталог вне репозитория, OneDrive/общих папок и
автоматической синхронизации. Пример для NTFS, без требования админ-прав:

```powershell
$signingDir = Join-Path $env:USERPROFILE 'ScreenTranslatorSigning'
New-Item -ItemType Directory -Path $signingDir -ErrorAction Stop
$account = [System.Security.Principal.WindowsIdentity]::GetCurrent().Name
icacls $signingDir /inheritance:r /grant:r "${account}:(OI)(CI)F"
if ($LASTEXITCODE -ne 0) { throw 'Сначала настройте права приватного каталога' }
.venv-release-tools\Scripts\python.exe tools/prepare_signed_release.py keygen --private-key "$signingDir\owner-ed25519.pem" --public-out "$signingDir\owner-public.json" --key-id owner-2026
```

Не выполняйте пример поверх существующего каталога без проверки его ACL. Ключ
сохраняется только в **зашифрованном PKCS8 PEM**, пароль запрашивается дважды через
`getpass`. Нужен длинный уникальный пароль (не менее 12 байт; лучше парольная фраза
из менеджера паролей). Файлы не перезаписываются. Запрет внутри checkout проверяется
по реальному пути, включая symlinks и другие Git-репозитории.

Сохраните зашифрованную резервную копию PEM отдельно, пароль — отдельно в менеджере
паролей. Не отправляйте PEM, пароль, скриншот содержимого или расшифрованный ключ в
чат, GitHub, Actions secrets, артефакты и логи. При частичной ошибке записи не
удаляйте существующий зашифрованный ключ автоматически: сохраните его и разберите
ошибку локально. Потерянный/скомпрометированный ключ требует отдельной процедуры.

Утилита выводит только **публичный отпечаток** `SHA256:<64 hex>`. Он вычисляется от
32 сырых байт публичного ключа. `owner-public.json` содержит только algorithm,
key_id, public_key_hex и fingerprint; это не приватный файл.

## 3. Вручную закрепить публичный ключ в лаунчере

Сверьте отпечаток вручную с записанным при генерации значением. Можно передать для
ревью **только** `owner-public.json` и публичный отпечаток. В отдельном PR после
вашей сверки добавляется:

```python
TRUSTED_KEYS = {
    "owner-2026": bytes.fromhex("<public_key_hex из отдельно проверенного owner-public.json>")
}
```

Это шаблон, не настоящий ключ. Никакой случайный ключ из тестов не подходит.
Текущий PR не заполняет trust store. Ревью/слияние остаются под вашим контролем.
После проверки ключа пересоберите `build_launcher.bat` и **вручную** установите
этот лаунчер. Уже установленный лаунчер с пустым trust store нельзя включить
одним флажком: ключ не берётся из настроек/манифеста/Интернета, самообновления
лаунчера здесь нет. Публичный ключ и подписанный Release нужны одновременно.

## 4. Подготовить окончательные ZIP

Соберите нужную версию переводчика (`build_exe.bat` и `build_exe.bat --argos`),
проверьте оба профиля и smoke/GUI. Выберите фактическую версию пакета `X.Y.Z`,
согласованную с приложением и будущим тегом `vX.Y.Z`. Утилита требует явный
`--version`, проверяет формат; она **не запускает непроверенный EXE**, чтобы
угадать версию. Подтвердите версию приложения сами на проверенной сборке.

Скопируйте окончательные ZIP в новую локальную папку выпуска. Измените только
имя файла, не содержимое ZIP:

```text
ScreenTranslator-X.Y.Z-ocr-windows-x64.zip
ScreenTranslator-X.Y.Z-argos-windows-x64.zip
```

Внутри по-прежнему `ScreenTranslator/ScreenTranslator.exe`, `_internal/`, README
и лицензия. Модели/ключи/настройки/история в ZIP не входят. Actions artifacts сами
по себе не доверенные обновления. Не распаковывайте и не пересобирайте архив после
получения его SHA/подписи. При любом изменении байтов нужна новая проверка и подпись.

## 5. Только владелец: разрешённый draft и реальные asset IDs

**Ни один draft/Release в рамках этой задачи не создавался.** Когда вы отдельно
разрешите подготовку настоящего выпуска, самостоятельно создайте **Draft Release**
в `xardas46rus-prog/ScreenTranslator` с тегом `vX.Y.Z`, нужным commit и загрузите
оба окончательных ZIP. Не нажимайте Publish на этом этапе.

Получите реальные ID и размеры загруженных assets через интерфейс GitHub или
локально авторизованный `gh` на вашем ПК:

```powershell
$draftId = Read-Host 'ID одобренного draft release'
gh api "repos/xardas46rus-prog/ScreenTranslator/releases/$draftId/assets" --jq '.[] | {id,name,size,browser_download_url}'
```

Это публичные метаданные assets, не API token. Используйте существующий локальный
вход GitHub; не вставляйте токен в команды/чат. Пока Release — draft, обычный
публичный `/releases/latest` его не видит: 404 здесь ожидаем. Если удалить ZIP и
загрузить снова, ID поменяется — старый манифест использовать нельзя.

## 6. Локально inspect → sign → verify

Ниже пример **для Argos**, значения задаёт владелец по реальной сборке/asset.
Повторите отдельно для OCR с его профилем, ZIP, ID и выходными файлами.

```powershell
$releaseVersion = Read-Host 'Версия окончательного ZIP (X.Y.Z)'
$archive = Read-Host 'Полный путь к неизменённому Argos ZIP'
$argosAssetId = Read-Host 'Реальный asset ID Argos ZIP из одобренного draft'
$releaseDir = Read-Host 'Локальный каталог для новых manifest/update файлов'
.venv-release-tools\Scripts\python.exe tools/prepare_signed_release.py inspect --archive "$archive" --version "$releaseVersion" --profile argos --asset-id "$argosAssetId" --out "$releaseDir\manifest-argos.json"
.venv-release-tools\Scripts\python.exe tools/prepare_signed_release.py sign --manifest "$releaseDir\manifest-argos.json" --archive "$archive" --private-key "$signingDir\owner-ed25519.pem" --key-id owner-2026 --out "$releaseDir\update-argos.json"
$verifiedFingerprint = Read-Host 'Ранее независимо сверенный публичный отпечаток SHA256:...'
.venv-release-tools\Scripts\python.exe tools/prepare_signed_release.py verify --manifest "$releaseDir\update-argos.json" --archive "$archive" --public-key "$signingDir\owner-public.json" --fingerprint "$verifiedFingerprint"
```

Проверяйте exit code после **каждой** команды (`$LASTEXITCODE` должен быть 0), не
продолжайте после ошибки. Файлы вывода создаются только новыми, не перезаписываются.
`inspect` проверяет структуру ZIP/CRC/PE AMD64, size, SHA-256 и текущую схему.
`sign` читает только зашифрованный Ed25519 PEM вне checkout, спрашивает пароль
интерактивно и перед записью повторно проверяет подпись/ZIP общим кодом лаунчера.
`verify` требует заранее сверенный fingerprint; не берите его вслепую из
непроверенного публичного файла. Сам ZIP во всех подкомандах открывается на чтение.

`manifest-*.json` — **неподписанная подготовительная информация**, она никогда не
принимается лаунчером. Подписанные оболочки `update-ocr.json` и `update-argos.json`
используют ровно контракт v1 из [LAUNCHER_RU.md](LAUNCHER_RU.md): те же canonical
байты, Ed25519, профиль, stable, windows-x64, min_launcher, URL/asset ID/size/SHA.

## 7. Ручная проверка и отдельное подтверждение публикации

Загрузите проверенные `update-ocr.json` / `update-argos.json` в тот же одобренный
draft, оставив ZIP без изменений. Перепроверьте ID/имена/размеры и локальную подпись
для **обоих** профилей. Убедитесь, что в assets нет PEM/секретов/моделей.
Только после вашего **отдельного разрешения на настоящий Release** вручную
публикуйте его как stable (не prerelease). Автоматических publish/merge в коде и CI нет.

На Windows 10 с лаунчером, уже содержащим проверенный публичный ключ:

1. Сохраните внешнюю portable-папку и модели. Нажмите «Первоначальная подписанная
   установка…», выберите другой пустой каталог и нужный профиль.
2. Проверьте доступную версию, stable, размер и «подпись Ed25519 подтверждена».
3. Нажмите «Установить» и подтвердите загрузку/установку. После **первой** подписанной
   установки проверенный EXE запустится. Внешняя папка и модели не изменяются.
4. Для следующих версий проверка только предлагает обновление, установка требует
   подтверждения. Последующие версии не запускаются скрыто. Закройте переводчик
   перед установкой/откатом.
5. Если нужна автоматическая **проверка**, включите «Проверять при старте». По
   умолчанию она off. Это не согласие на скрытую загрузку или замену EXE.
6. Проверьте реальный перевод Argos и затем «Откат». Highwater остаётся новым:
   старый сетевой релиз повторно не устанавливается. Вернуться можно только к
   сохранённой подписанной версии через явный откат, не отключая подписи.

## Диагностика и что пока не подтверждено

- «Доверенный ключ не задан»: нужен проверенный PUBLIC key и пересобранный
  лаунчер, не пароль/приватный ключ в настройках.
- HTTP 403: proxy/сетевая политика или лимит GitHub API; в этой облачной среде
  `api.github.com/graphql` также блокировал создание PR. Проверяйте фактический
  ответ и настройки сети, не отключайте TLS и проверку подписи.
- HTTP 404: публичный Release ещё не опубликован, нет нужного asset или он
  недоступен. Draft и временный Actions artifact не заменяют stable Release.
- «Актуальная версия»: проверенный Release уже установлен. После отката сообщение
  отдельно объясняет запрет replay: ждите более новую версию.
- Подпись/хэш/профиль/asset ID не совпали: установка запрещена; не обходите защиту,
  исправьте и заново подпишите метаданные владельцем.

Офлайн-тест проверяет весь цикл metadata → manifest → ZIP → staging → pointer →
первый запуск/обновление/rollback с **тестовым** ключом и mocked transport на
Windows/Linux. Настоящий сетевой update, ваши модели и установку с реальным
ключом/Release следует считать **не проверенными**, пока вы не выполните пункты
выше после отдельного разрешения публикации. Ключи и релизы эта задача не создаёт.
